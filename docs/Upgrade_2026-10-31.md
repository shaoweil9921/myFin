## 2026-11-01 — Attempt 2 (Option B: pin to 2026.10.5)

### Why not just run `/update` again
`/update` and `update.run` **cannot pin a version**. They resolve `update.channel` → registry target → `latest` = **2026.10.9**, which your Node refuses. There is no `tag`/`target` parameter on the control-plane `update.run` RPC (its `target` field is **Git-sha only**). Only the CLI's `--tag` can pin.

Also checked — **no update channel maps to a Node-24.19.0-compatible build**:

| Channel / tag | Resolves to | Needs Node | Compatible with 24.19.0? |
|---|---|---|---|
| `stable` | 2026.10.9 | `>=24.22.1` | ❌ |
| `extended-stable` | 2026.9.36 | `>=24.22.1` | ❌ |
| `beta` | 2026.10.10-beta.4 | `>=24.22.1` | ❌ |
| `beta` (later tag) | 2026.10.10-beta.5 | `>=24.16.0` | ✅ but a moving target |
| `--tag 2026.10.5` | 2026.10.5 | `>=24.16.0` | ✅ **recommended** |

The updater correctly refused to let an in-gateway command replace the package that
owns it. **This is expected behaviour, not a bug** — and it confirms the preflight
guard works.

### ✅ Correct command — run it yourself in a real terminal
The agent's exec shell **is** inside the gateway process tree, so it can never run
this. Open a standalone **Windows Terminal / PowerShell** (not via OpenClaw) and run:

```powershell
openclaw update --tag 2026.10.5 --yes
```

Same owning account, same installation, same state/config paths. The docs call this
the "independent Terminal outside the Gateway process tree" path. It hands off to the
managed helper, which parks the Scheduled Task service, swaps the package, and
restarts it.

Expected console output: the helper acknowledges with **exit code 75** (`EX_TEMPFAIL`)
— that means "accepted, background work running", *not* failure. Then use the
printed follow-up commands:
```powershell
openclaw update status --json
openclaw gateway status --deep
```
